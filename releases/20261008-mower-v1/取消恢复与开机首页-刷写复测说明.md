# 割刀取消恢复与开机MOWER首页

2026-10-08。本版只需更新FS-i6X遥控器，继续使用前一版已验收的底盘固件。

本文写于中间版本，命令已改用本包顶层文件。当时的遥控器镜像 `fs-i6x-cancel-recovery-home.bin` 就是本包的 `fs-i6x-mower-v1.bin`，只改了文件名。

## 刷写

| 设备 | 文件 | 写入地址 |
|---|---|---|
| FS-i6X 遥控器 | `fs-i6x-mower-v1.bin` | `0x08000000` |

刷写前：先备份遥控器镜像/模型。断开割刀动力，固定车轮并保持底盘急停；只更新遥控器。

遥控器先进入 USB DFU，用 `dfu-util -l` 确认只连了目标遥控器、Internal Flash 是 alt 0（不是就换成实际值），在本目录执行：

```bash
dfu-util -a 0 -s 0x08000000:leave -D fs-i6x-mower-v1.bin
```

必须看到 `File downloaded successfully`。

镜像128312字节，保留已验收的校准、CH2端点、CH10 0.4～1.8m/s与SETm/s显示。无需清EEPROM，无需重刷底盘。确认下载成功后正常开机。

BIN／HEX 写法、备份、读回和排障见[通用刷写指南](../../docs/flashing.md)。

## 为什么取消会等这么久

这不是固定10秒冷却：完整上行命令约90×20ms=1.8秒，下行回执约17×250ms=4.25秒，正常一次事务就约6秒，旧回执排队与调度还会加时。实际割刀输出在CH4回中后按底盘既有状态机停止；STOPPING等待的是取消协议确认，不是直接测量刀盘机械停转。

旧代码还有两个等待问题：启动发送已完成却仍等待启动回执，取消无法越过它；丢失命令或回执后没有重试，只能等到60秒超时。代码和宿主故障注入已复现此路径，但没有用户实机RF抓包，因此不能认定每次超过10秒都由同一种丢包导致。

## 新行为

- CH4回中取消可以在当前发送帧完成后优先发出，不再等丢失的启动回执。完整在途帧不会被截断。
- Cancel没有有效回执时，以同一动作身份间隔8秒重试，最多2次；不重复执行割刀动作，也不重发启动Confirm。新鲜回执还在接收时可顺延重试。
- 再左打CH4仍立即显示新提示。取消未确认时OK不缓存、不授权；成功取消后> OK，需要再按一次才能重新启动。
- 等待超过10秒或取消失败时显示STOP NO REPLY，含义是没有获得有效的取消成功确认；此时新启动保持禁止。60秒绝对截止不因重试延长，到期也不自动放行。
- 每次开机默认进入照片中的MOWER首页，即SOC/BAT/SETm/s/ACT/BLADE OUTPUT/CH7 GEAR/LINK/RUN/FAULT页面；仍可切换DATA等页。必要的安全检查/校准提示先完成，不绕过它们。切到其他页后关机，下一次仍从MOWER首页开始。

本版不承诺任何RF环境下10秒内获得回执，尤其不能把STOPPING消失等同于机械刀盘停转证据。

## 复测与记录

割刀动力继续隔离，以控制器输出状态检查，必要时在调试器记录g_exp3_hil.pending.kind/action/generation、waiting、cancel_retries、cancel_failed、rtt_ms及matches，不占用SERVO/SENS串口加入打印。

| 项目 | 通过标准 | 记录 |
|---|---|---|
| 开机首页 | 通过必要安全检查后直接显示照片中的MOWER首页 | 待测 |
| 页切换后重启 | 在DATA/通道监视器关机，重启仍进入MOWER；有效校准与模型保留 | 待测 |
| 未确认取消 | CH4左打不按OK，回中再左打仍及时提示 | 待测 |
| 确认后立即取消 | 左打→OK→立即回中→立即左打，新提示及时出现；取消完成后才显示> OK | 待测 |
| 连续开关5轮 | 每轮回中取消后可再次提示，没有重复授权；记录回中至> OK的间隔 | 待测 |
| 忙期间OK | STOPPING/STOP NO REPLY期间反复OK不能缓存或启动；成功后必须再按OK | 待测 |
| 迟到回执 | 原启动回执迟到不能把新待确认动作自动变成已接受 | 待测 |
| 无有效取消确认 | 超过10秒显示STOP NO REPLY；仍不自动开放启动，不能因超时自行启动 | 待测 |
| 故障恢复 | 断链/急停/碰撞按原安全流程停止并重新授权；保持左打或旧OK不得恢复启动 | 待测 |
| 既有行走/显示 | CH2端点、CH10最低0.4m/s、SETm/s与正常CH1/CH4行程保持正确 | 待测 |

分别记录“CH4回中→实际输出清零”和“回中→收到取消成功确认/> OK”；本次优化针对第二个过程，不能用其代替第一个过程的安全验收。故障注入丢帧/丢回执在主机测试已完成，实机进行时必须保持动力隔离。

若STOP NO REPLY持续：先回中CH4，急停并确认割刀输出停止；记录pending/重试/失败状态。保持割刀动力隔离，可重启遥控器重新建立会话，等待READY与新鲜运行反馈后按原流程重新授权；不要在CH4左打时用重启当作启动捷径。若重复超过10秒，请记录是启动后立即取消还是运行后取消、两阶段时间和上述计数，以区分实际丢帧、排队或控制器否决。

## 本机验证

全套主机回归和底盘Debug ARM构建通过；消息校验最终修改后host再次通过，遥控器ARM构建通过且增量无warning/error。另有真实控制器/HMI/割刀状态机的集成丢包测试：首个取消回执整条丢失后，同身份重试收到缓存回执，取消只执行一次、无新授权/刀盘输出。默认首页测试执行真实启动前段而非替代实现。

Flash128312/131072 B，RAM15692/16384 B。SVN preflight通过，有3项既有工作区告警；日志随镜像交付。本版还没有实机刷写、LCD/RF验收。
